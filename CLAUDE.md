# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

One codebase for the Hebrew (RTL) ordering sites of several home food businesses: a React/Vite frontend (`frontend/`) and an ASP.NET Core (.NET 10) + EF Core + PostgreSQL API (`backend/`). Each business is deployed separately (its own Render service, Neon database and secrets) from the same code. The product spec and decisions are in `docs/PLAN.md`; deployment in `docs/DEPLOY.md`. Commit and PR text is written in English; user-facing text is Hebrew.

> **Every user-facing change updates the feature guide in the same PR.** A PR that adds, removes or changes anything a customer or the admin can see or do is not done until [`docs/food-sites-feature-guide.html`](docs/food-sites-feature-guide.html) describes it in Hebrew and English, with screenshots taken from demo data. If a PR has no guide impact, say why in the PR checklist. This applies to every feature PR, including ones started from a project thread or a skill; #47 (dish order) and #50 (usage report) merged without it and had to be documented afterwards. Details: [Feature guide maintenance](#feature-guide-maintenance-required).

## Platform status and rules

This repo started as a copy of `kuskus-shel-ima` (history imported) and is being made generic. **Read `docs/MIGRATION-PLAN.md` first**: it lists the phases, which are done, and the target layout (`sites/<site-id>/` per business). Phase 1 renamed the projects to `FoodSite.*`; Phase 2 moved each business's identity into `sites/<site-id>/` (`site.json`, `theme.css`, logo, `public/`, `i18n/he.json` overrides, `seed/`), chosen by `SITE` at build time, with `sites/_template/` for a new one. Phase 3 added `sites/grape-leaves-eliel/` as the second site and moved every colour that differed between the sites into `theme.css` variables. Phase 4 added feature flags (`site.json` → `features`, overridden by the `FeatureFlags` table). Phase 5 made CI build an image per site and added per-site Render services with a canary rollout. Phase 6 added the ops API (`/api/ops/*`, `docs/OPS-API.md`) the separate console uses, with a per-site console token, and the admin's "report a problem" page. `sites/cigars-shiraz/` was the first site added with the `new-food-site` skill (`.claude/skills/new-food-site/SKILL.md`), which is how a new business gets a site. `sites/_shared/seed/` holds seeds any site can list as `"../_shared/seed/<name>.json"` (the drinks, pictured in Cloudinary's `common/drinks`); it is not a site, so `check-sites` and CI's image matrix skip it, and both Dockerfiles copy it next to `site/`. Cookie names, the JWT issuer, WhatsApp template names, Cloudinary folders and the order-draft key are built from the site id. Update this file in the same PR that changes any of this.

- Shared code never names a business or checks which site it runs as (`if (siteId == ...)`). Business-specific values (name, texts, palette, logo, WhatsApp template names, seeds) belong in `sites/<site-id>/`; behaviour only some businesses want goes behind a feature flag, off by default (see Feature flags below).
- Every migration reaches every site: make it backward compatible (expand, then contract), and keep `AppDbContextModelSnapshot.cs` in sync.
- This repo is public. Never commit secrets, client data, or a business's photos and texts collected for a demo; those go to Cloudinary or stay local.
- Merge conflicts on your own PR are yours to resolve, immediately and without asking: when a PR you opened conflicts with `main` (or `main` moved on), merge `origin/main` into the branch (no rebase or force-push), resolve every conflict keeping both sides' intent (for the feature guide, take `main`'s file and re-add your section under the next free number), rerun lint, build and tests, push, and carry on. Only ask when both sides changed the same logic and keeping either would lose behaviour.
- Mark a phase's checkboxes in `docs/MIGRATION-PLAN.md` in the PR that completes them.
- `node scripts/check-sites.mjs` (run in CI) fails when a site folder is incomplete, a site's `theme.css` lacks a variable the shared CSS uses, a site overrides a `he.json` key the shared file lacks, or a site's id, name, emoji or template names appear in shared code.

## Feature guide maintenance (required)

The reusable customer/admin feature catalog is [`docs/food-sites-feature-guide.html`](docs/food-sites-feature-guide.html). It targets small food businesses: **Hebrew by default, RTL, with a complete English switch**. Keep both languages, accessible labels, search, category filters, image enlargement and print support working. Document one business's capabilities, not the multi-site wrapper.

- In every PR that adds, removes or changes customer/admin behavior, update the affected feature descriptions and screenshots in the same PR. For changes with no guide impact, state why in the PR checklist.
- After a PR merges, review the merged changes against the guide. If they were not already documented, prepare a focused documentation PR; do not automatically merge it. A merge-triggered ChatGPT automation can perform this follow-up; this file itself does not launch Claude or a background job.
- At the start of a Claude session, run `node scripts/check-feature-guide.mjs`. If the last review is at least **3 days** old, or product files have changed since the recorded commit, review those changes before finishing the session. The SessionStart hook prints the same reminder. Do not interrupt an unrelated urgent fix; explicitly record a blocked review instead of pretending it was completed.
- Read `docs/feature-guide-review.json` for the last genuinely reviewed commit/date. Compare against current source; update the marker only after reviewing all intervening relevant changes. Keep screenshot capture dates separate: a text review must not make old screenshots appear new. Fetch missing history when permitted; otherwise report that comparison is blocked.
- Capture customer and admin screens where the feature has those views. Use local/staging **synthetic data**. Never commit credentials, review tokens, real customer details, order/payment data or private contact information. Omitted captures in the imported guide must remain explicitly marked until safe replacements exist. Do not alter production settings, create production orders or send messages to obtain screenshots.
- Preserve honest evidence labels: observed, code-verified, unconfigured, sign-in required or capture unavailable. Never invent a screenshot or claim a full flow was tested when it was not. Keep source links and applicable limits accurate.
- Keep the HTML standalone (embedded images; no external scripts), validate Hebrew/English text and direction, search/filter behavior, image enlargement, source links and print output. Run `node scripts/check-feature-guide.mjs --check` before committing. Do not rewrite or recapture unchanged images solely to change the review date.

The checked-in review marker deliberately retains the original 8 October 2026 snapshot until a subsequent source review is completed. See [`docs/FEATURE-GUIDE.md`](docs/FEATURE-GUIDE.md) for opening and maintaining it.

## Commands

Frontend (`cd frontend`):
- `SITE=<site-id>` picks the site folder for `dev`, `build` and `test` (default `_template`; the Docker images require it)
- `npm run dev` — Vite on :5173, proxies `/api` to `localhost:5000` (override with `API_PROXY_TARGET`)
- `npm run build` — `tsc -b && vite build`; this is also the typecheck (CI builds every site)
- `npm run lint` — oxlint (`.oxlintrc.json`)
- `npm test` — vitest once; single file: `npx vitest run src/order/model.test.ts`; single test: add `-t "<name>"`

Backend (`cd backend`, solution `FoodSite.slnx`):
- `dotnet build`, `dotnet run --project src/FoodSite.Api` (:5000; needs `src/FoodSite.Api/appsettings.Development.json` from `appsettings.Example.json`)
- `dotnet test` — single class/test: `dotnet test --filter "FullyQualifiedName~OrdersTests"`
- `dotnet run --project src/FoodSite.Api -- hash-password '<pw>'` — admin password hash for `Admin__PasswordHash`
- Migrations: `dotnet ef migrations add <Name> --project src/FoodSite.Api --output-dir Data/Migrations`. `Program.cs` throws without a 32+ byte `Jwt:Secret`, and without a valid `Site:Id`, so for design-time `dotnet ef` commands set `Jwt__Secret=<32+ chars>`, `Site__Id=dev` and a dummy `ConnectionStrings__Default` in the environment. `dotnet ef migrations has-pending-model-changes --project src/FoodSite.Api` verifies the snapshot matches the model.

Whole stack: `SITE=<site-id> docker compose up --build` (site :8080, admin `/admin` with user name and password `admin`, API :5000, Postgres :5432).

`/check` (`.claude/commands/check.md`) runs all of the above checks.

### Cloud sessions
`.claude/hooks/session-start.sh` installs `dotnet-sdk-10.0` from Ubuntu's apt (Microsoft's download hosts are blocked by the network policy), restores packages, installs `dotnet-ef` to `~/.dotnet/tools`, runs `npm install`, and starts `dockerd`. ## Architecture

**One origin in production.** The root `Dockerfile` builds the frontend into the API's `wwwroot`; `Program.cs` serves static files and falls back to `index.html` for non-`/api` paths. Deployed to Render with Neon Postgres: one service per site in `render.yaml`, each with its own database and secrets. Every service has Render's auto-deploy off: after CI passes on `main`, `.github/workflows/deploy.yml` deploys the first service (the canary) through its Render deploy hook, then the others through theirs once the canary's `/api/health` reports the new commit (see `docs/DEPLOY.md`). `.github/workflows/keep-alive.yml` pings `/api/health` between 09:00 and 21:00 Israel time, only for the site ids in the GitHub variable `KEEP_ALIVE_SITES` (interval in `KEEP_ALIVE_INTERVAL_MINUTES`; set on GitHub, not in the repo), so those free services don't sleep. Locally, docker-compose runs the frontend separately behind nginx (`frontend/nginx.conf`) proxying `/api`.

**Backend (`backend/src/FoodSite.Api`)**
- `Sites/SiteFolder` loads the site folder (`Site:Directory`, or `./site` in the image) into configuration under `Site:` (above appsettings.json, below environment variables); `SiteOptions` (`Site:Id`, required) is what shared code uses instead of naming a business. `UseSiteDefaults` on `JwtOptions`, `CookieOptions` and `WhatsAppOptions` fills unset values from the id.
- `Program.cs` wires everything: two JWT bearer schemes reading tokens from httpOnly cookies — admin (`<siteId>_admin`, default scheme, role `Admin`) and client (`UserTokenService.Scheme`, cookie `<siteId>_user`, separate audience so a client token never authorizes admin endpoints). Rate-limit policies are named constants on `PublicControllerBase` and `AdminAuthController`.
- Feature flags: `Sites/Features` lists the known flags; a site turns one on in `site.json` → `features` (anything unlisted is off; an unknown name stops the app), and a row in the `FeatureFlags` table overrides that. `FeatureFlags` (scoped service) answers which are on; `GET /api/site` returns them as `features`; endpoints are guarded with `[RequireFeature(Features.X)]` (404 `featureDisabled`). A new flag means: a constant in `Features` (and `All`), the `Feature` type in `frontend/src/api/site.ts`, the flag in each site's `site.json` that wants it, and `ApiFactory` turning it on if existing tests need it.
- Ops API for the console (`Controllers/Ops/OpsController`, contract in `docs/OPS-API.md`; update it with any change): a third authentication scheme (`Ops/OpsToken`, `OpsAuthenticationHandler`) reads `Authorization: Bearer fso_…` and compares its SHA-256 with `Settings.OpsTokenHash`. Only `/api/ops` asks for that scheme and it asks for nothing else, so the token and admin/client sessions never stand in for each other. The master makes, replaces or revokes the token (`/api/admin/ops-token`, the master-only section at the end of `/admin/settings`); it is shown once. Endpoints: `version`, `summary` (per period and per status; `statuses` picks what counts, default everything but cancelled), `usage` (the admin's usage report, built by `Usage/UsageReportBuilder`), `recommendations` and `feedback` (list, mark handled), `features` (read, override or clear a `FeatureFlags` row). Changes are audited as `console`. `Feedback` rows come from the admin's **דיווח על בעיה** page (`/admin/feedback`, `FeedbackController`).
- Two admins per site (`Auth/AdminActor`): the site owner (user name `Admin:OwnerUsername`, hash in `Settings.AdminPasswordHash`, changed from the admin, seeded from `Admin:PasswordHash`) and the master (`Admin:MasterUsername` + `Admin:MasterPasswordHash`, configuration only, the same on every site; can reset the owner's password via `PUT /api/admin/owner-password`). The session token carries an `actor` claim; a token without one is rejected.
- Audit trail: `AppDbContext.SaveChangesAsync` writes an `AuditEntry` (actor, time, entity, key, label, changed fields old/new as JSON) for every change saved during a request to `/api/admin/*` (`Audit/AuditTrail`; password hashes recorded without values), plus a `LoggedIn` entry per login. `ExecuteUpdate`/`ExecuteDelete` bypass it, so admin endpoints load and save entities instead. `GET /api/admin/audit` (the **יומן שינויים** tab) is read-only; nothing edits or removes entries.
- Site styles: `Sites/SiteStyles` lists the looks (`classic`, `street`, `tiles`): fonts, shapes and layout only, colours stay in `theme.css`. `tiles` also changes the order page's markup: `DishCard`/`DishGroupCard` (`order/DishCard.tsx`) render square tiles with a round add button when `useSiteStyle()` is `tiles`, open the choices in a `Modal` only for a dish that needs them (`needsDialog`: set options, open by default, or add-ons/questions the client must settle) and otherwise add it at once with a small customize icon button; tapping a tile that is not in the order does nothing (only its round add button adds it), and `Modal` renders through a portal into `<body>` so presses inside a dialog never reach the tile it was opened from; the dish dialogs pass `closeButton` for an X in the corner, and pressing a tile's picture opens its dialog without adding the dish. The admin picks one in Settings (`Settings.SiteStyle`, `PUT /api/admin/settings` → `style`); until then the site's `site.json` → `settings.style` applies (not copied into Settings), else `classic`. `GET /api/site` returns the effective `style`; `ClientLayout` sets `<html data-style>` (client pages only, never the admin) and `frontend/src/styles/<style>.css` (loaded by `main.tsx`, fonts self-hosted from `@fontsource`) restyles shared classes under `[data-style='<style>']`. A new style means: a constant in `SiteStyles` (and `All`), `SiteStyle`/`SITE_STYLES` in `frontend/src/api/site.ts`, its stylesheet, its `admin.settings.styles.*` texts and preview in the picker, and `styles` in `scripts/check-sites.mjs`.
- Basket and order summary: the order page registers its basket with `components/cartNav.ts` (`useRegisterCart`, provider in `ClientLayout`), and `TopBar` shows the bold basket button (badge = `dishTotals` main + side + drinks, plus the total) only while a page has registered one. `order/CartSheet.tsx` is the `Modal` it opens: each chosen dish with its picture, amount stepper, remove, a details toggle and "edit" (closes the sheet and scrolls to the dish's card through `[data-dish-id]` / `[data-variants]`), a continue button and the running total. `order/OrderSummary.tsx` is the read-only list above the send button on every layout (`summaryLines` in `order/model.ts`). In the tiles style a group tile rotates through its main dish's pictures and each variant's (`TileMedia`, `groupSlides`). The search box and the category chips / steps header sit in one `.order-sticky` block pinned under the top bar (`--top-bar-height`); the hero banner is outside `.order-main`, so the side total's panel starts below it. None of this touches the hero logo.
- Category jump bar: the one-page order flows (`page`, `continue`) with more than one category show `CategoryJumpBar` (`order/`) pinned under the top bar, chips that scroll to `#category-<id>` and mark the category being read; the paged flow has its own steps header and does not show it; there is no setting for it. - Order layout: two settings next to the style, both independent of it (`Sites/OrderLayout`): `OrderTotalPosition` (`bottom`, or `side`: a sticky panel at the left of the screen in Hebrew from 64rem up, narrow screens keep the bottom bar) and `OrderFlow` (`page`, or `steps`: one category at a time with arrows and chips, the last step is the order form; a signed-in client with a saved address already has the contact block collapsed). They follow the style's pattern: nullable `Settings` columns, `site.json` → `settings.orderTotalPosition` / `orderFlow` as the default (not copied), the effective values in `GET /api/site` and `GET/PUT /api/admin/settings`, `useOrderLayout()` on the frontend, `OrderLayoutSection` in the Appearance page (each admin section saves only its own fields so defaults aren't pinned), and `orderTotalPositions` / `orderFlows` in `scripts/check-sites.mjs`. A new value means a constant in `OrderLayout` (and its list), the type in `frontend/src/api/site.ts`, its `admin.settings.orderTotals.*` / `orderFlows.*` texts and the CSS under `.order-page[data-total]` or `.order-steps`.
- Order layout: two settings next to the style, both independent of it (`Sites/OrderLayout`): `OrderTotalPosition` (`bottom`, or `side`: a sticky panel at the left of the screen in Hebrew from 64rem up, narrow screens keep the bottom bar) and `OrderFlow` (`page`, `continue`: the whole menu on one page with the order details hidden until a "המשך לפרטי ההזמנה" button is pressed, or `steps`: one category at a time with arrows and chips, the last step is the order form; a signed-in client with a saved address already has the contact block collapsed). They follow the style's pattern: nullable `Settings` columns, `site.json` → `settings.orderTotalPosition` / `orderFlow` as the default (not copied), the effective values in `GET /api/site` and `GET/PUT /api/admin/settings`, `useOrderLayout()` on the frontend, `OrderLayoutSection` in the Appearance page (each admin section saves only its own fields so defaults aren't pinned), and `orderTotalPositions` / `orderFlows` in `scripts/check-sites.mjs`. A new value means a constant in `OrderLayout` (and its list), the type in `frontend/src/api/site.ts`, its `admin.settings.orderTotals.*` / `orderFlows.*` texts and the CSS under `.order-page[data-total]` or `.order-steps`.
- Corners: `Sites/Corners` (`square`, `slight`, `rounded`, `round`; `rounded` is the original look) follows the same pattern as the order layout: nullable `Settings.Corners`, `site.json` → `settings.corners` as the default (not copied), the effective value in `GET /api/site` and `GET/PUT /api/admin/settings`, `useCorners()` and `CornersSection` in the Appearance page, and `corners` in `scripts/check-sites.mjs`. `ClientLayout` sets `<html data-corners>` (client pages only); `index.css` turns it into `--corner-scale` (multiplies `--radius` and every fixed corner radius in `index.css` and `styles/*.css`) and `--radius-pill` (pill shapes); circles (`50%`) stay round. A new rounded corner in the shared CSS uses `var(--radius)`, `calc(<size> * var(--corner-scale))` or `var(--radius-pill)`, never a bare length.
- Colours: `Sites/Palettes` (`site` = the theme.css colours, plus `olive`, `berry`, `ocean`, `sunset`, `graphite`, `rose`) and the admin's own colours follow the corners' pattern with three nullable `Settings` columns (`Palette`, `CustomColors` as a JSON object keyed by `Palettes.ColorKeys`, `LineWidth` 1-4; sending `{}` / `0` clears the last two), `site.json` → `settings.palette` as the default (not copied), the effective values in `GET /api/site` and `GET/PUT /api/admin/settings`, `palettes` in `scripts/check-sites.mjs`. The colour values of the palettes live only in `frontend/src/site/palettes.ts`; `ClientLayout` turns palette + custom colours (custom win) into inline CSS variables on `<html>` (client pages only, removed on unmount): the `--color-*` theme variables plus optional `--btn-bg`, `--btn-bg-hover`, `--btn-text`, `--bar-bg`, `--bar-text`, `--banner-text`, `--dish-bg`, `--dish-text`, `--line-width`, all used in the shared CSS with a fallback so a site with none set looks as before (`check-sites` only requires theme variables used without a fallback). Text colours below WCAG AA contrast (4.5) on their background are swapped for black or white (`ensureReadable`) and `ColorsSection` (Appearance page) says which. A new palette means an id in `Palettes.All`, `PALETTES` and `PALETTE_COLORS`, its `admin.settings.palettes.*` texts and `palettes` in `scripts/check-sites.mjs`; a new colour element means a key in `Palettes.ColorKeys` and `COLOR_KEYS`, a variable in `colorVariables`, its `admin.settings.colorKeys.*` text and CSS that reads the variable.
- Finish: `Sites/Finish` (font pair `standard`/`friendly`/`elegant`, shadows `standard`/`none`/`soft`/`strong`, spacing `standard`/`compact`/`spacious`) are three nullable `Settings` columns (`FontPair`, `ShadowStrength`, `Spacing`; null = `standard`, no `site.json` default), returned as `font`, `shadows`, `spacing` by `GET /api/site` and the settings API; `FinishSection` (Appearance page) saves them on their own; `ClientLayout` sets `<html data-font data-shadows data-spacing>` and `styles/finish.css` (loaded last, so it wins over `street.css`/`tiles.css`) turns them into font and shadow variables and spacing overrides. Colours and finish must show the same in every style: when a style hard-codes a colour (`street.css`, `tiles.css`), make it read the colour variables of `palettes.ts` (`--btn-*`, `--bar-*`, `--dish-*`, `--page-bg`, `--color-gold` derived from the accent) with the old value as the fallback.
- Colours also apply to the admin (`admin/useAdminLook.ts`, called by `AdminLayout`: palette, custom colours, line thickness, font and shadows from `GET /api/site`, updated live by `announceLook` after the Appearance sections save; the style, corners and spacing stay client-only). A custom colour can be `=<element>` (copy another element's colour, `Palettes.IsCopy`/`HasCopyCycle` validate, `mergeColors` resolves); `categoryBackground` → `--category-bg` is the block behind a category's dishes. `Settings.TileGroups` (`framed`/`minimal`, `Finish.TileGroups`, `<html data-tile-groups>`, picked in `StyleSection` once tiles is chosen) makes the tiles style drop the frame around each category.
- `RequireRequestHeaderMiddleware`: every POST/PUT/DELETE to `/api` must carry `X-Food-Site-Request: 1` (CSRF guard). The frontend's `apiFetch` and the test `ApiFactory.CreateApiClient` add it.
- Controllers: `PublicController` (`/api/site`, `/api/menu`), `OrdersController` (`POST /api/orders`), `AccountController` (`/api/account/*`, phone-only login — no verification code), `ReviewsController` (`/api/reviews`: approved reviews, and the review page behind a per-order link `/r/<token>`), `Controllers/Admin/*` (all derive `AdminControllerBase`, `[Authorize(Roles=Admin)]`). WhatsApp messages to a client are sent by hand: `MessageTemplatesController` holds the admin's templates, and the Orders tab composes one (`admin/messages/compose.ts`: first name, text, review link) into a wa.me link.
- Errors are **codes, not text**: `Errors` collects `{field: [code]}` and `Invalid(...)` returns a ValidationProblem; whole-request failures are `{ code }` (e.g. `Conflict("categoryNotEmpty")`). The frontend lowercases field names and translates codes via `he.json` (`errors.*`). Adding a new code means adding its Hebrew text.
- `Orders/OrderBuilder` prices orders server-side from DB dishes (client prices are never trusted); order lines snapshot dish name/option/price so later edits don't change history. Dishes/categories are soft-deleted (`IsHidden`). `Orders/SupplyCalendar` + `SiteClock` compute open supply dates (weekday, per-day cutoff, closed dates) in `Site:TimeZone`, and each date's one-hour slots from the day's working hours (`SupplyDayHours`: up to 6 non-overlapping ranges per day, an end of 00:00 is midnight; the legacy `DeliveryFrom`/`DeliveryTo` columns are copied by the migration and no longer read). Shabbat and holiday rules (`Settings.ShabbatRules` JSON, `Sites/ShabbatRules`, admin `ShabbatRulesController`, the **שבתות וחגים** block of `/admin/settings`): for Shabbat and for holidays separately, the eve's end of activity and the last rest day's start (no change, closed, fixed time, or whole/half hours before candle lighting / after the stars come out) in a chosen city; `Orders/ShabbatSchedule` cuts the day's ranges (`SupplyCalendar.OpenDates` takes it), `Orders/JewishCalendar` knows the holidays (as kept in Israel) and the sun times (NOAA formula, candle lighting 18 min before sunset, 40 in Jerusalem, 30 in Haifa; the end is the sun 8.5° below the horizon). Slot timing (`Orders/SlotTiming`, `Settings.SlotMinutes` 15/30/60, `AlignSlots`, `DeliveryLeadMinutes`, `PickupLeadMinutes`, edited in the general settings): slots are cut by the slot length, with `AlignSlots` starting each range on the next multiple of it; a slot gets `DeliveryOk`/`PickupOk` from the lead time of each way (a slot must start that long from now; without a lead it is open until it ends) and a date with no slot ok for either is not offered. When a day works until 23:59/00:00 and the next enabled, open day has a range starting at 00:00 (after the Shabbat rules), that range's slots follow the day's own marked with their `Date`; the client sends `OrderInput.DeliveryHourDate` and the order is saved on that date. A client picks a slot when the day has hours; `Settings.OrdersPerHour` caps a slot only softly: `GET /api/hour-availability` tells the order page a picked hour is full (it is never shown in advance), the order still goes through, and the admin's orders list marks the orders past the cap (`HourFull`). `Settings.PortionsPerSupplyDate` is a hard cap shared by all dishes (`Orders/DailyPortions`: unit dishes that are not sides or add-on only): the menu folds what is left of it into each counted dish's `remaining`, and an order past it fails with `portionLimitReached`.
- Variants and add-on settings (feature `advancedDishes`, on in every site's `site.json`; it only gates the admin form, the order page shows whatever the admin set): `Dish.MainDishId` makes a dish a variant shown in its main dish's card (main dish's images and description, its category; `UseMainDishPrice` prices it with the main dish's mode and options; variants are ordered and listed as dishes of their own, and a main dish with variants is not ordered itself). `Dish.IsYesNo` is ordered once, no amount. `DishAddOn` carries per-parent `Price` (zero allowed, default option only), `MaxQuantity` per ordered unit of the parent (like `AddOnGroup.MaxUnits`), `IsCheckbox`, `DisplayOrder` and an `AddOnGroup` (`Name`, `MaxUnits`; a check box or a weight counts one unit). A variant also offers its main dish's add-ons (`Orders/DishRules`). `OrderBuilder` enforces all of it (`addOnLimit`, `addOnGroupLimit`). Each ordered unit of a dish sold by units can have add-ons of its own: the order page sends `OrderLineInput.AddOnUnits` (one entry per unit, limits per unit; wrong count → `addOnUnitsInvalid`), the builder merges units with the same add-ons into one line (`Selection.extraUnits` in `order/model.ts` holds units 2..n, the select in each unit copies another unit's add-ons); the shared `AddOns` list still works, scaled by quantity; on the order page a dish that offers add-ons (or has questions) shows one closed panel per unit with its add-ons, remark and answers; each unit must be adjusted (an add-on picked, or `Selection.confirmed` via "אישור ללא התאמות") before the order can be sent (`unadjustedDishes`), unless the admin made it optional for the dish (`Dish.AdjustmentOptional`, on by default for new and existing dishes, a variant follows its main dish; - Dish groups (no feature flag): the admin's **קבוצות מנות** page (`/admin/dish-groups`, `DishGroupsController`, `DishGroup` + `DishGroupDish`, `dishGroupsApi`) holds any number of named groups, each a selection of dishes ordered on their own (not variants or add-on-only) from any categories; a dish can be in several groups and stays in its category. `GET /api/menu` returns `groups` (id, name, dish ids in menu order; empty groups left out). - Delivery fee (no feature flag: the admin picks the method in the general settings, `Settings.DeliveryPricing` is `simple` = "regular" until they choose `zones` = "advanced"). Everything about delivery area, service cities, fee text and the fixed fee (`Settings.DeliveryFeeAmount`, added to the total of a delivery to a service city) belongs to **regular** and is shown in `GeneralSection` and on the order page only then; the advanced setting shows none of the regular messages (service-city warning, area and fee texts) and ignores `ServiceCities`. `Delivery/DeliveryQuoter` is the one place that decides the fee, for the order page's preview (`POST /api/delivery-quote`, `useDeliveryQuote`, 600 ms after the last key, or at once on the "calculate" button) and again for the order itself. Regular: a service city (or any city when none are listed) gets `DeliveryFeeAmount`, another city is `outside` (fee 0, the order gets `NeedsReview` and the message says the business will phone about the price); the order page adds the regular fee locally from `GET /api/site` (`serviceCities`, `deliveryFeeAmount`). The address is geocoded by `IAddressGeocoder` (`NominatimGeocoder`: free, one request a second, cached, tries the full address, then free text, then the street or only the city, the last two marked `Approximate`; the tests use `FakeGeocoder`), `DeliveryZones.Quote` checks the point (a blocked zone holding it always wins, else the lowest priority; a point in no zone is `blocked`; no zones drawn means free; an address that could not be placed is `unknown`). "Find my location" (`AddressFields`, `POST /api/delivery-quote/locate`, `IAddressGeocoder.ReverseAsync`) fills city, street and house number from the device position and brings the quote for that point (the order itself re-geocodes the address text, so the two can differ slightly). Large-order discount (`Settings.DeliveryDiscountMinOrder`, and `DeliveryBaseFee` for the advanced method; the regular method's fixed fee is its own base fee; `Delivery/DeliveryDiscount.Amount` decides it, mirrored by `order/deliveryDiscount.ts` for the preview): once the dishes reach the threshold the base fee comes off the fee, never below zero, so a near zone priced at the base fee is free and a far one pays the rest. The order saves `DeliveryFee` already reduced plus `Order.DeliveryDiscount`; every place that shows the delivery line adds the note (`order/DeliveryFeeNote.tsx`, `OrderMessages.FeeText` for WhatsApp and the owner mail), and the order page shows "משלוחים חינם בהזמנות מעל X" (asterisk note under the advanced method). The driver pages show totals only. `GET /api/site` returns the effective `deliveryPricing` and `deliveryFeeAmount`; `GET/PUT /api/admin/settings` carry both, and `GeneralSection` saves them with the rest.

**Frontend (`frontend/src`)**
- Routes in `App.tsx`: client pages under `ClientLayout` (`/` is the order page); admin under `/admin` wrapped in `RequireAdmin` (unlinked from the client site).

From it the admin makes a driver link (`DriverLinks.tsx` → `DriverRoutesController`): a `DriverRoute` with a 192-bit random token and its stops in the report's order, working through the day after its supply day or until removed. The driver's page `/d/<token>` (`driver/`, `DriverController`, no login) shows only those stops and reports each one onto the order (`DeliveryOutcome`, note, proof photo in Cloudinary `<siteId>/deliveries`, payment with `PaidByDriver`; a payment the admin recorded stays theirs); the Orders tab shows the report.

Any internal link click, logging out and closing the tab then ask "save and continue / continue without saving / stay" while a registered form is dirty; saving runs every dirty form's `save`. A field's explanation is never a line of text under it: it goes in `Info` (a small "i" button beside the label, title or legend, in a `.with-info` line, never inside a `<label>`, heading or legend that names a control; give a fieldset `aria-labelledby` its legend text so the button stays out of its name). `FormBlock` folds one topic of a long form under its title with an `Info` about it in the title line (the dish form has one per topic, only the basics open; a block opens by itself when a field in it fails validation).

- Tests: vitest + Testing Library in jsdom. Tests sit next to the feature (`*.test.tsx`).
