# Architecture reference

Detailed per-area notes for the food-sites codebase, moved out of `CLAUDE.md` to keep each chat's context small. `CLAUDE.md` links here: read the section for the area you are about to change (search for its name), and update the section in the same PR that changes the area.

## Platform history and site folders

This repo started as a copy of `kuskus-shel-ima` (history imported) and is being made generic. **Read `docs/MIGRATION-PLAN.md` first**: it lists the phases, which are done, and the target layout (`sites/<site-id>/` per business). Phase 1 renamed the projects to `FoodSite.*`; Phase 2 moved each business's identity into `sites/<site-id>/` (`site.json`, `theme.css`, logo, `public/`, `i18n/he.json` overrides, `seed/`), chosen by `SITE` at build time, with `sites/_template/` for a new one. Phase 3 added `sites/grape-leaves-eliel/` as the second site and moved every colour that differed between the sites into `theme.css` variables. Phase 4 added feature flags (`site.json` → `features`, overridden by the `FeatureFlags` table). Phase 5 made CI build an image per site and added per-site Render services with a canary rollout. Phase 6 added the ops API (`/api/ops/*`, `docs/OPS-API.md`) the separate console uses, with a per-site console token, and the admin's "report a problem" page. `sites/cigars-shiraz/` was the first site added with the `new-food-site` skill (`.claude/skills/new-food-site/SKILL.md`), which is how a new business gets a site. `sites/_shared/seed/` holds seeds any site can list as `"../_shared/seed/<name>.json"` (the drinks, pictured in Cloudinary's `common/drinks`); it is not a site, so `check-sites` and CI's image matrix skip it, and both Dockerfiles copy it next to `site/`. Cookie names, the JWT issuer, WhatsApp template names, Cloudinary folders and the order-draft key are built from the site id. Update `CLAUDE.md` and this file in the same PR that changes any of this.

## Architecture

**One origin in production.** The root `Dockerfile` builds the frontend into the API's `wwwroot`; `Program.cs` serves static files and falls back to `index.html` for non-`/api` paths. Deployed to Render with Neon Postgres: one service per site in `render.yaml`, each with its own database and secrets. Every service has Render's auto-deploy off: after CI passes on `main`, `.github/workflows/deploy.yml` deploys the first service (the canary) through its Render deploy hook, then the others through theirs once the canary's `/api/health` reports the new commit (see `docs/DEPLOY.md`). `.github/workflows/keep-alive.yml` pings `/api/health` between 09:00 and 21:00 Israel time, only for the site ids in the GitHub variable `KEEP_ALIVE_SITES` (interval in `KEEP_ALIVE_INTERVAL_MINUTES`; set on GitHub, not in the repo), so those free services don't sleep. Locally, docker-compose runs the frontend separately behind nginx (`frontend/nginx.conf`) proxying `/api`.

**Backend (`backend/src/FoodSite.Api`)**
- `Sites/SiteFolder` loads the site folder (`Site:Directory`, or `./site` in the image) into configuration under `Site:` (above appsettings.json, below environment variables); `SiteOptions` (`Site:Id`, required) is what shared code uses instead of naming a business. `UseSiteDefaults` on `JwtOptions`, `CookieOptions` and `WhatsAppOptions` fills unset values from the id.
- `Program.cs` wires everything: two JWT bearer schemes reading tokens from httpOnly cookies — admin (`<siteId>_admin`, default scheme, role `Admin`) and client (`UserTokenService.Scheme`, cookie `<siteId>_user`, separate audience so a client token never authorizes admin endpoints). Rate-limit policies are named constants on `PublicControllerBase` and `AdminAuthController`.
- Feature flags: `Sites/Features` lists the known flags; a site turns one on in `site.json` → `features` (anything unlisted is off; an unknown name stops the app), and a row in the `FeatureFlags` table overrides that. `FeatureFlags` (scoped service) answers which are on; `GET /api/site` returns them as `features`; endpoints are guarded with `[RequireFeature(Features.X)]` (404 `featureDisabled`). A new flag means: a constant in `Features` (and `All`), the `Feature` type in `frontend/src/api/site.ts`, the flag in each site's `site.json` that wants it, and `ApiFactory` turning it on if existing tests need it.
- Ops API for the console (`Controllers/Ops/OpsController`, contract in `docs/OPS-API.md`; update it with any change): a third authentication scheme (`Ops/OpsToken`, `OpsAuthenticationHandler`) reads `Authorization: Bearer fso_…` and compares its SHA-256 with `Settings.OpsTokenHash`. Only `/api/ops` asks for that scheme and it asks for nothing else, so the token and admin/client sessions never stand in for each other. The master makes, replaces or revokes the token (`/api/admin/ops-token`, the master-only section at the end of `/admin/settings`); it is shown once. Endpoints: `version`, `summary` (per period and per status; `statuses` picks what counts, default everything but cancelled), `cancellations` (cancelled orders with their reason and details), `clients` (registered client accounts with phone, email, city and order count), `usage` (the admin's usage report, built by `Usage/UsageReportBuilder`), `recommendations` and `feedback` (list, mark handled), `features` (read, override or clear a `FeatureFlags` row). Changes are audited as `console`. `Feedback` rows come from the admin's **דיווח על בעיה** page (`/admin/feedback`, `FeedbackController`).
- Two admins per site (`Auth/AdminActor`): the site owner (user name `Admin:OwnerUsername`, hash in `Settings.AdminPasswordHash`, changed from the admin, seeded from `Admin:PasswordHash`) and the master (`Admin:MasterUsername` + `Admin:MasterPasswordHash`, configuration only, the same on every site; can reset the owner's password via `PUT /api/admin/owner-password`). The session token carries an `actor` claim; a token without one is rejected.
- Cancelling an order always needs a reason (`StatusInput.CancelReason`, `Order.CancelReason` max 300 and `CancelledAt`; `400 cancelReason: required`, the admin's `CancelForm`): the business pays no sales commission on cancelled orders, and the console checks them. Reopening an order clears both.
- Audit trail: `AppDbContext.SaveChangesAsync` writes an `AuditEntry` (actor, time, entity, key, label, changed fields old/new as JSON) for every change saved during a request to `/api/admin/*` (`Audit/AuditTrail`; password hashes recorded without values), plus a `LoggedIn` entry per login. `ExecuteUpdate`/`ExecuteDelete` bypass it, so admin endpoints load and save entities instead. `GET /api/admin/audit` (the **יומן שינויים** tab) is read-only; nothing edits or removes entries.
- Site styles: `Sites/SiteStyles` lists the looks (`classic`, `street`, `tiles`): fonts, shapes and layout only, colours stay in `theme.css`. `tiles` also changes the order page's markup: `DishCard`/`DishGroupCard` (`order/DishCard.tsx`) render square tiles with a round add button when `useSiteStyle()` is `tiles`, open the choices in a `Modal` only for a dish that needs them (`needsDialog`: set options, open by default, or add-ons/questions the client must settle) and otherwise add it at once with a small customize icon button; tapping a tile that is not in the order does nothing (only its round add button adds it), and `Modal` renders through a portal into `<body>` so presses inside a dialog never reach the tile it was opened from; the dish dialogs pass `closeButton` for an X in the corner, and pressing a tile's picture opens its dialog without adding the dish. The admin picks one in Settings (`Settings.SiteStyle`, `PUT /api/admin/settings` → `style`); until then the site's `site.json` → `settings.style` applies (not copied into Settings), else `classic`. `GET /api/site` returns the effective `style`; `ClientLayout` sets `<html data-style>` (client pages only, never the admin) and `frontend/src/styles/<style>.css` (loaded by `main.tsx`, fonts self-hosted from `@fontsource`) restyles shared classes under `[data-style='<style>']`. A new style means: a constant in `SiteStyles` (and `All`), `SiteStyle`/`SITE_STYLES` in `frontend/src/api/site.ts`, its stylesheet, its `admin.settings.styles.*` texts and preview in the picker, and `styles` in `scripts/check-sites.mjs`.
- Basket and order summary: the order page registers its basket with `components/cartNav.ts` (`useRegisterCart`, provider in `ClientLayout`), and `TopBar` shows the bold basket button (badge = `dishTotals` main + side + drinks, plus the total) only while a page has registered one. `order/CartSheet.tsx` is the `Modal` it opens: each chosen dish with its picture, amount stepper, remove, a details toggle and "edit" (closes the sheet and scrolls to the dish's card through `[data-dish-id]` / `[data-variants]`), a continue button and the running total. `order/OrderSummary.tsx` is the read-only list above the send button on every layout (`summaryLines` in `order/model.ts`). In the tiles style a group tile rotates through its main dish's pictures and each variant's (`TileMedia`, `groupSlides`). The search box and the category chips / steps header sit in one `.order-sticky` block pinned under the top bar (`--top-bar-height`); the hero banner is outside `.order-main`, so the side total's panel starts below it. None of this touches the hero logo.
- Category jump bar: the one-page order flows (`page`, `continue`) with more than one category show `CategoryJumpBar` (`order/`) pinned under the top bar, chips that scroll to `#category-<id>` and mark the category being read; the paged flow has its own steps header and does not show it; there is no setting for it.
- Order layout: two settings next to the style, both independent of it (`Sites/OrderLayout`): `OrderTotalPosition` (`bottom`, or `side`: a sticky panel at the left of the screen in Hebrew from 64rem up, narrow screens keep the bottom bar) and `OrderFlow` (`page`, `continue`: the whole menu on one page with the order details hidden until a "המשך לפרטי ההזמנה" button is pressed, or `steps`: one category at a time with arrows and chips, the last step is the order form; a signed-in client with a saved address already has the contact block collapsed). They follow the style's pattern: nullable `Settings` columns, `site.json` → `settings.orderTotalPosition` / `orderFlow` as the default (not copied), the effective values in `GET /api/site` and `GET/PUT /api/admin/settings`, `useOrderLayout()` on the frontend, `OrderLayoutSection` in the Appearance page (each admin section saves only its own fields so defaults aren't pinned), and `orderTotalPositions` / `orderFlows` in `scripts/check-sites.mjs`. A new value means a constant in `OrderLayout` (and its list), the type in `frontend/src/api/site.ts`, its `admin.settings.orderTotals.*` / `orderFlows.*` texts and the CSS under `.order-page[data-total]` or `.order-steps`.
- Corners: `Sites/Corners` (`square`, `slight`, `rounded`, `round`; `rounded` is the original look) follows the same pattern as the order layout: nullable `Settings.Corners`, `site.json` → `settings.corners` as the default (not copied), the effective value in `GET /api/site` and `GET/PUT /api/admin/settings`, `useCorners()` and `CornersSection` in the Appearance page, and `corners` in `scripts/check-sites.mjs`. `ClientLayout` sets `<html data-corners>` (client pages only); `index.css` turns it into `--corner-scale` (multiplies `--radius` and every fixed corner radius in `index.css` and `styles/*.css`) and `--radius-pill` (pill shapes); circles (`50%`) stay round. A new rounded corner in the shared CSS uses `var(--radius)`, `calc(<size> * var(--corner-scale))` or `var(--radius-pill)`, never a bare length.
- Colours: `Sites/Palettes` (`site` = the theme.css colours, plus `olive`, `berry`, `ocean`, `sunset`, `graphite`, `rose`) and the admin's own colours follow the corners' pattern with three nullable `Settings` columns (`Palette`, `CustomColors` as a JSON object keyed by `Palettes.ColorKeys`, `LineWidth` 1-4; sending `{}` / `0` clears the last two), `site.json` → `settings.palette` as the default (not copied), the effective values in `GET /api/site` and `GET/PUT /api/admin/settings`, `palettes` in `scripts/check-sites.mjs`. The colour values of the palettes live only in `frontend/src/site/palettes.ts`; `ClientLayout` turns palette + custom colours (custom win) into inline CSS variables on `<html>` (client pages only, removed on unmount): the `--color-*` theme variables plus optional `--btn-bg`, `--btn-bg-hover`, `--btn-text`, `--bar-bg`, `--bar-text`, `--banner-text`, `--dish-bg`, `--dish-text`, `--line-width`, all used in the shared CSS with a fallback so a site with none set looks as before (`check-sites` only requires theme variables used without a fallback). Text colours below WCAG AA contrast (4.5) on their background are swapped for black or white (`ensureReadable`) and `ColorsSection` (Appearance page) says which. A new palette means an id in `Palettes.All`, `PALETTES` and `PALETTE_COLORS`, its `admin.settings.palettes.*` texts and `palettes` in `scripts/check-sites.mjs`; a new colour element means a key in `Palettes.ColorKeys` and `COLOR_KEYS`, a variable in `colorVariables`, its `admin.settings.colorKeys.*` text and CSS that reads the variable.
- Finish: `Sites/Finish` (font pair `standard`/`friendly`/`elegant`, shadows `standard`/`none`/`soft`/`strong`, spacing `standard`/`compact`/`spacious`) are three nullable `Settings` columns (`FontPair`, `ShadowStrength`, `Spacing`; null = `standard`, no `site.json` default), returned as `font`, `shadows`, `spacing` by `GET /api/site` and the settings API; `FinishSection` (Appearance page) saves them on their own; `ClientLayout` sets `<html data-font data-shadows data-spacing>` and `styles/finish.css` (loaded last, so it wins over `street.css`/`tiles.css`) turns them into font and shadow variables and spacing overrides. Colours and finish must show the same in every style: when a style hard-codes a colour (`street.css`, `tiles.css`), make it read the colour variables of `palettes.ts` (`--btn-*`, `--bar-*`, `--dish-*`, `--page-bg`, `--color-gold` derived from the accent) with the old value as the fallback.
- Colours also apply to the admin (`admin/useAdminLook.ts`, called by `AdminLayout`: palette, custom colours, line thickness, font and shadows from `GET /api/site`, updated live by `announceLook` after the Appearance sections save; the style, corners and spacing stay client-only). A custom colour can be `=<element>` (copy another element's colour, `Palettes.IsCopy`/`HasCopyCycle` validate, `mergeColors` resolves); `categoryBackground` → `--category-bg` is the block behind a category's dishes. `Settings.TileGroups` (`framed`/`minimal`, `Finish.TileGroups`, `<html data-tile-groups>`, picked in `StyleSection` once tiles is chosen) makes the tiles style drop the frame around each category.
- `RequireRequestHeaderMiddleware`: every POST/PUT/DELETE to `/api` must carry `X-Food-Site-Request: 1` (CSRF guard). The frontend's `apiFetch` and the test `ApiFactory.CreateApiClient` add it.
- Controllers: `PublicController` (`/api/site`, `/api/menu`), `OrdersController` (`POST /api/orders`), `AccountController` (`/api/account/*`, phone-only login — no verification code; login and registration are one step, see Accounts and addresses), `ReviewsController` (`/api/reviews`: approved reviews, and the review page behind a per-order link `/r/<token>`), `Controllers/Admin/*` (all derive `AdminControllerBase`, `[Authorize(Roles=Admin)]`). WhatsApp messages to a client are sent by hand: `MessageTemplatesController` holds the admin's templates, and the Orders tab composes one (`admin/messages/compose.ts`: first name, text, review link) into a wa.me link.
- Errors are **codes, not text**: `Errors` collects `{field: [code]}` and `Invalid(...)` returns a ValidationProblem; whole-request failures are `{ code }` (e.g. `Conflict("categoryNotEmpty")`). The frontend lowercases field names and translates codes via `he.json` (`errors.*`). Adding a new code means adding its Hebrew text.
- `Orders/OrderBuilder` prices orders server-side from DB dishes (client prices are never trusted); order lines snapshot dish name/option/price so later edits don't change history. Dishes/categories are soft-deleted (`IsHidden`). `Orders/SupplyCalendar` + `SiteClock` compute open supply dates (weekday, per-day cutoff, closed dates) in `Site:TimeZone`, and each date's one-hour slots from the day's working hours (`SupplyDayHours`: up to 6 non-overlapping ranges per day, an end of 00:00 is midnight; the legacy `DeliveryFrom`/`DeliveryTo` columns are copied by the migration and no longer read). Shabbat and holiday rules (`Settings.ShabbatRules` JSON, `Sites/ShabbatRules`, admin `ShabbatRulesController`, the **שבתות וחגים** block of `/admin/settings`): for Shabbat and for holidays separately, the eve's end of activity and the last rest day's start (no change, closed, fixed time, or whole/half hours before candle lighting / after the stars come out) in a chosen city; `Orders/ShabbatSchedule` cuts the day's ranges (`SupplyCalendar.OpenDates` takes it), `Orders/JewishCalendar` knows the holidays (as kept in Israel) and the sun times (NOAA formula, candle lighting 18 min before sunset, 40 in Jerusalem, 30 in Haifa; the end is the sun 8.5° below the horizon). Slot timing (`Orders/SlotTiming`, `Settings.SlotMinutes` 15/30/60, `AlignSlots`, `DeliveryLeadMinutes`, `PickupLeadMinutes`, edited in the general settings): slots are cut by the slot length, with `AlignSlots` starting each range on the next multiple of it; a slot gets `DeliveryOk`/`PickupOk` from the lead time of each way (a slot must start that long from now; without a lead it is open until it ends) and a date with no slot ok for either is not offered. When a day works until 23:59/00:00 and the next enabled, open day has a range starting at 00:00 (after the Shabbat rules), that range's slots follow the day's own marked with their `Date`; the client sends `OrderInput.DeliveryHourDate` and the order is saved on that date. A client picks a slot when the day has hours; `Settings.OrdersPerHour` caps a slot only softly: `GET /api/hour-availability` tells the order page a picked hour is full (it is never shown in advance), the order still goes through, and the admin's orders list marks the orders past the cap (`HourFull`). `Settings.PortionsPerSupplyDate` is a hard cap shared by all dishes (`Orders/DailyPortions`: unit dishes that are not sides or add-on only): the menu folds what is left of it into each counted dish's `remaining`, and an order past it fails with `portionLimitReached`.
- Variants and add-on settings (feature `advancedDishes`, on in every site's `site.json`; it only gates the admin form, the order page shows whatever the admin set): `Dish.MainDishId` makes a dish a variant shown in its main dish's card (main dish's images and description, its category; `UseMainDishPrice` prices it with the main dish's mode and options; variants are ordered and listed as dishes of their own, and a main dish with variants is not ordered itself). `Dish.IsYesNo` is ordered once, no amount. `DishAddOn` carries per-parent `Price` (zero allowed, default option only), `MaxQuantity` per ordered unit of the parent (like `AddOnGroup.MaxUnits`), `IsCheckbox`, `DisplayOrder` and an `AddOnGroup` (`Name`, `MaxUnits`; a check box or a weight counts one unit). A variant also offers its main dish's add-ons (`Orders/DishRules`). `OrderBuilder` enforces all of it (`addOnLimit`, `addOnGroupLimit`). Each ordered unit of a dish sold by units can have add-ons of its own: the order page sends `OrderLineInput.AddOnUnits` (one entry per unit, limits per unit; wrong count → `addOnUnitsInvalid`), the builder merges units with the same add-ons into one line (`Selection.extraUnits` in `order/model.ts` holds units 2..n, the select in each unit copies another unit's add-ons); the shared `AddOns` list still works, scaled by quantity; on the order page a dish that offers add-ons (or has questions) shows one closed panel per unit with its add-ons, remark and answers; each unit must be adjusted (an add-on picked, or `Selection.confirmed` via "אישור ללא התאמות") before the order can be sent (`unadjustedDishes`), unless the admin made it optional for the dish (`Dish.AdjustmentOptional`, on by default for new and existing dishes, a variant follows its main dish; `GET /api/menu` returns the effective value); with it optional, required questions need no answer either (`OrderBuilder`, `unansweredDishes`) and the units (or the one remark of a dish with no add-ons or questions) wait behind a "הצג/הסתר התאמת מנות" button in `DishCard`, which shows them open only for a dish with add-ons or questions whose adjustment is required; a variant with no pictures, options, add-ons or questions is a small box side by side with others like it (`dish-variant--compact`), and "apply to the rest" copies a unit to every unit not yet adjusted; a dish with neither has one remark sent as `OrderLineInput.Note`; each unit also carries a name or remark (`OrderItem.Note`, max `OrderBuilder.NoteMaxLength`; units with different notes stay separate lines; shown in the admin orders, driver page and WhatsApp text); `PUT /api/admin/dishes/{id}` with `addOns`/`addOnGroups` replaces the dish's own add-ons, leaving them out keeps them. `DishAddOn.LinkedFromAddOn` marks links ticked on the add-on's own form ("תוספת למנות אחרות", `DishInput.ParentDishIds`, seed `AddOnOf`): only those show and change there, so an add-on set up on its parent's form is the parent's alone. A variant is never offered under itself through its main dish's add-ons.
- Sub-dish extras (`DishAddOn`, key `ParentDishId + AddOnDishId + Slot`): the same add-on can be offered again under one dish (`Slot` 1, 2..., a required `Label` each, shown as "name (label)" and snapshotted that way on the order line); the order page keeps an add-on's selection under `addOnKey(dishId, slot)` (the dish id for slot 0) and sends `AddOnInput.Slot`. `ShowImage` shows the add-on's picture in the unit panel. `OverLimitPrice` on a link (needs `MaxQuantity`) and on an `AddOnGroup` (needs `MaxUnits`) turns the limit into a price: units above it become order lines of their own named "… (מעבר למכסה)" at that price (`OrderBuilder.AddOnsOf`, mirrored by `unitAddOnTotals` in `order/model.ts`; keep them in step). `IsDefault` picks the add-on for every new unit (`startSelection`/`fitAddOns`, `Selection.defaultsApplied`) until the client takes it off; a seed's add-on can set `isDefault` too.
- Fixed options (sizes or weights, `DishOption`: label, amount, full price, one default): `Dish.OptionsTitle` is an optional heading over them on the order page ("בחרו גודל"; else "בחירה עבור <dish>") and `Dish.ShowOptionDifference` shows each option as what it adds to the default option's price (`optionPriceText` in `order/format.ts`; the default shows its full price). Prices stay absolute everywhere (basket, summary, order lines); a variant priced like its main dish takes both from it, and both are cleared when the dish switches to a free amount.
- Dish questions (no feature flag; a dish has none until the admin adds them): `DishQuestion` (`Text`, `Kind`: `Text`/`Number`/`Date`/`YesNo`/`SingleChoice`/`MultiChoice`, `Choices` as `text[]`, `ShowAsDropdown` for a single choice, `IsRequired`, `DisplayOrder`, `DefaultAnswer`: a choice or `yes`/`no`, already picked on the order page through `answerOf` in `order/model.ts` until the client changes it), edited in the dish form (`admin/dishes/QuestionsSection.tsx`, `questionForm.ts`) and sent whole as `DishInput.Questions` (ids kept; left out keeps them). A variant asks its main dish's questions first (`DishRules.Questions`); `GET /api/menu` returns them per dish. The order page asks them per ordered unit (`Selection.answers`, like notes) and sends `AnswerInput` (`Value`, or `Choices` for a multiple choice; yes/no as `yes`/`no`, dates `yyyy-MM-dd`) on the line or each `UnitAddOnsInput`; `OrderBuilder` checks them (`answerRequired`, `answerInvalid`) and snapshots them as text onto `OrderItem.Answers` (owned JSON column, null on lines saved before questions existed); units with different answers stay separate lines. Answers show in the admin orders, driver report, driver page (`components/ItemAnswers.tsx`) and WhatsApp text.
- Accounts and addresses (no feature flag): `POST /api/account/login` with a phone that has no account makes one (`LoginDto.IsNew`), so nothing but the phone is required (`register` and `google/register` only add optional details; an address that is started needs city, street and house number). The frontend then shows `GetToKnowYou` (LoginPage) once, skippable. A client has up to 10 `UserAddress` rows (`Label`, parts, `IsDefault`; endpoints `/api/account/addresses`, `/{id}`, `/{id}/default`), the `User.City/Street/HouseNumber/Apartment/Address` columns mirror the default (`SyncDefault`) so older readers keep working; the first address is the default and deleting the default promotes the oldest. The order page's `SavedAddressPicker` fills the fields and asks the delivery quote to run again. After an order `POST /api/account/remember` keeps the name and address: for the logged-in client on the account, for a guest in `GuestDetails` by phone (applied and removed when that phone gets an account); the order must be under 2 hours old with the same phone, and a phone that already has an account is only written to by its own session. Since login has no code, phone ownership is not verified anywhere.
- Sign in with Google (no feature flag; off until `Google__ClientId` is set): `Auth/GoogleSignIn` (`GoogleOptions`, `IGoogleTokenVerifier`/`GoogleTokenVerifier`: checks a Google ID token's signature against Google's cached public keys, the issuer and the audience; no client secret, no redirect). `GET /api/site` returns `googleClientId` (null hides the button); `POST /api/account/google` logs in by `User.GoogleSub`, else links the one account whose `Email` equals Google's *verified* email and has no `GoogleSub` yet, else answers `registration` (name, email) and `POST /api/account/google/register` takes the token again plus the usual profile (phone and address are still required) and creates the user. Never link on an unverified email or take over an account tied to another Google id. The frontend's `account/GoogleSignInButton.tsx` loads Google's script and is used on `LoginPage`; tests replace the verifier with `FakeGoogleVerifier` and the button with a stub.
- Accessibility (no feature flag, on every site): `accessibility/AccessibilityMenu.tsx` (mounted by `ClientLayout`, never in the admin or driver page) is a small fixed button with a compact menu (text size, high contrast, grayscale, highlighted links, readable font, no animation, big cursor, reset). `accessibility/prefs.ts` keeps the choices in `localStorage` (`<siteId>.accessibility`) and sets `<html data-a11y-*>` plus the root font size; `styles/accessibility.css` (loaded last) turns them into styles, high contrast overriding the palette variables with `!important`. `components/motion.ts` (`useReducedMotion`) makes the carousels stop too. The statement page `/accessibility` (`pages/AccessibilityStatementPage.tsx`, linked from the footer and the menu) has shared Hebrew text in `he.json` → `accessibility.statement` and the contact from `GET /api/accessibility`: the coordinator the admin set in the contacts page (`AccessibilityAdminController`, `Settings.Accessibility*`, its own endpoint so it stays apart from the settings DTO), else the main contact. A widget alone does not make a site comply with Israeli law (SI 5568 / WCAG AA): new UI keeps labels, focus outlines and contrast. Run axe on new pages.
- Dietary tags (no feature flag; a dish has none until the admin ticks some): `Dish.DietaryTags` (`text[]`, ids from `Sites/DietaryTags.All`, kept in that order, unknown ids → 400 `invalid`) is edited in the dish form's foldable block "באילו אפשרויות המנה מגיעה" (a check box each, plus `Dish.DietaryTagsSingle`: only one may be picked) and sent whole as `DishInput.DietaryTags` / `DietaryTagsSingle` (left out keeps them); `GET /api/menu` returns it per dish. `Orders/DishRules.Questions` also appends one optional question over the dish's own tags (multiple choice, or single choice with `DietaryTagsSingle`, where the order page adds a "המנה הרגילה" radio that answers nothing) (id `DietaryTags.QuestionId` = -1, Hebrew labels in `DietaryTags.Labels`), so the client can pick a special version or keep the regular dish: it is answered and snapshotted like any dish question (no price change) and its unit panel opens by itself. The order page shows them only as that question: an icon (`order/DietaryTags.tsx` `DietaryIcon`, matched to the choices by position in `dish.dietaryTags`) beside each check box. A new tag means an id in `DietaryTags.All`, `DIETARY_TAGS` in `api/catalog.ts`, its icon in `DietaryTags.tsx`, its Hebrew label in `DietaryTags.Labels` and its `dietaryTags.<id>` text. Menu seeds may list `dietaryTags`.

- Passing info messages (saved, draft restored, order filled) are toasts: `useToast()` (`components/toast.ts`, provider in `App.tsx`). Errors and warnings tied to a field or an order stay inline (`Status`, `.notice--warning`).
- Driver report (`admin/route/`, `/admin/orders/route?date=`): built only from the admin orders list. `plan.ts` orders the day's deliveries by requested hour, then nearest next address, and times each stop; travel is guessed from the address text (same street / city / other city), with no map service. From it the admin makes a driver link (`DriverLinks.tsx` → `DriverRoutesController`): a `DriverRoute` with a 192-bit random token and its stops in the report's order, working through the day after its supply day or until removed. The driver's page `/d/<token>` (`driver/`, `DriverController`, no login) shows only those stops and reports each one onto the order (`DeliveryOutcome`, note, proof photo in Cloudinary `<siteId>/deliveries`, payment with `PaidByDriver`; a payment the admin recorded stays theirs); the Orders tab shows the report.
- Unsaved changes in the admin: `AdminLayout` wraps its pages in `UnsavedChangesProvider`; a form with a save button calls `useUnsavedChanges(dirty, save)` (`admin/unsaved.ts`, `save` returns whether it saved; `useDirty(value)` compares a loaded value with what it was when loaded or last saved). Any internal link click, logging out and closing the tab then ask "save and continue / continue without saving / stay" while a registered form is dirty; saving runs every dirty form's `save`. A new admin form with a save button registers itself the same way. The browser's back button is not caught.
- Admin screens use `admin/hooks.ts` (`useLoad`, `useErrorMessage`) and shared `admin/ui.tsx` components. A field's explanation is never a line of text under it: it goes in `Info` (a small "i" button beside the label, title or legend, in a `.with-info` line, never inside a `<label>`, heading or legend that names a control; give a fieldset `aria-labelledby` its legend text so the button stays out of its name). `FormBlock` folds one topic of a long form under its title with an `Info` about it in the title line (the dish form has one per topic, only the basics open; a block opens by itself when a field in it fails validation).
- Admin reordering: dishes (within their category, `Dish.DisplayOrder`) and dish images (the first is the main one) are reordered by dragging a grip (`admin/sortable.ts` `useDragSort`, pointer events so touch works) or with `MoveButtons`; both send the whole new order (`PUT /api/admin/dishes/order`, `PUT /api/admin/dishes/{id}/images/order`, 409 `listChanged` when it is stale). `GET /api/menu` lists dishes category by category in that order.
- All UI text goes through i18next keys in `i18n/he.json` (no hard-coded Hebrew in components); `i18n/index.ts` keeps `<html lang dir>` in sync so another language is just a new JSON file.
- Tests: vitest + Testing Library in jsdom. Page tests render the whole app at a route with `renderAt(path)` (`test/render.tsx`) and stub the network with `fakeApi({ 'METHOD /regex/path': handler })` (`test/fakeApi.ts`), which throws on any unexpected request; `adminSession` and `invalid(...)` are helpers, sample menu data is in `test/catalogData.ts`. Tests sit next to the feature (`*.test.tsx`).

A feature typically touches: entity + migration + snapshot, controller DTO/validation, backend test, `api/*.ts` types, the component, `he.json`, `test/catalogData.ts`, a frontend test, and the feature guide (`docs/food-sites-feature-guide.html`, both languages and a screenshot).
